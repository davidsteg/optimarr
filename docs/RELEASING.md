# Releasing Optimarr

These rules apply to every release, whoever cuts it.

## Versioning

- Versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html):
  - **major** for anything that breaks an existing setup: removed or renamed settings, API changes,
    a required new service, data that does not carry over;
  - **minor** for new features and behaviour changes that keep existing setups working;
  - **patch** for bug fixes only.
- The version lives in three places that must match: `VERSION`, `backend/Cargo.toml` and
  `frontend/package.json` (plus `Cargo.lock` and `frontend/package-lock.json`, regenerated by the
  tools).
- A released version is never reused or changed. Tags are never moved or deleted; a broken release
  is fixed by the next patch version.

## Changelog and release notes

- `CHANGELOG.md` follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Changes land
  under `## [Unreleased]` as they are merged; a release renames that section to
  `## [x.y.z] - YYYY-MM-DD` and opens a new, empty `## [Unreleased]` above it.
- Each version's section is the GitHub Release notes, so write it for the people running Optimarr,
  not for developers:
  - start with one or two sentences saying what the release means for them;
  - group changes under `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed` and `Security`;
  - describe what a user sees or has to do, naming settings and pages as they appear in the UI;
  - add an `Upgrading` section with numbered steps whenever a user has to do anything, and a
    `Breaking changes` section for every major version.

## Publishing

Merging a version bump to master publishes it; nobody pushes tags by hand. The
[Release workflow](../.github/workflows/release.yml):

1. checks the version numbers and that the CHANGELOG section exists, is dated and lists changes,
2. runs the frontend checks and the backend tests,
3. pushes a `linux/amd64` image to Docker Hub (`davidsteg/optimarr`) and GHCR
   (`ghcr.io/davidsteg/optimarr`) tagged `X.Y.Z`, `X.Y`, `X` and `latest`. The floating tags only
   move forward: an older version published later gets only its `X.Y.Z` tag (and `X.Y` if it is
   the newest patch of that minor version),
4. creates the `vX.Y.Z` tag on the merged commit and the GitHub Release, with the CHANGELOG section,
   the `docker pull` line and a compare link to the previous version,
5. checks that the tag points at the released commit, the release is published and every image tag
   exists for linux/amd64.

A release is only done when that run is green and the tag, the GitHub Release and the image are
all visible. A version that was missed can be published by running the workflow by hand under
Actions with the tag and the commit to tag.
